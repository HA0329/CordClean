白名单而非黑名单

辖区（allowRoot）机制

插件必须在 setup 阶段声明「我只会清这些目录」，否则连自己扫描出来的文件也删不掉。辖区随插件 fiber 自动回收。

ctx.effect(() => {
  const disposers = sources().map(s =>
    ctx.pathPolicy.addRoot(s.path, 'temp'))
  return () => disposers.forEach(d => d())
})
即使插件被替换或写错路径，也只能影响它声明过的目录。
唯一入口

票据防伪 + 执行器二次复核

CleanTicket 用模块私有 Symbol 做运行期身份校验，外部无法伪造。类型标注挡不住 any，所以执行器每次执行前还会逐项 recheck()。

  • 签发：只有 compensate 模块能构造票据；
  • 执行：只认 isCleanTicket() 为真的对象；
  • 复核：规范化 + 策略 + 存在性，不信任票据内容。
路径判定顺序与「写法绕过」

check(path) 的 6 步

  1. 空路径 / 非绝对路径 → 拒绝
  2. 驱动器根目录（C:\）→ 拒绝
  3. 位于保护根内 或保护根的祖先 → 拒绝
  4. 文件名在黑名单（pagefile.sys 等）→ 拒绝
  5. 不在任何辖区 / 用户扫描根内 → 拒绝
  6. 否则 → 允许
只判断「是否在保护目录内」不够：删除 C:\Windows 这样的祖目录仍会连带删掉 System32，因此同时判断两个方向。

三种文件系统「写法差异」

写法实际语义处理
System32.忽略尾部点逐段去掉尾部 . / 空格
PROGRA~18.3 短名解析短名并加入保护列表

自测发现的高危缺陷（D-01）：辖区内联接点导致越界删除 路径字符串完全落在辖区内，但辖区目录里的 NTFS 联接点指向了外部 —— 字符串检查通过，删除却命中了辖区外文件。 修复：删除前从父目录向上 lstat 到辖区根，任一祖先为链接即整项拒绝；该检查按目录缓存，不影响删除吞吐。 修复后补充了回归测试，并保留在安全测试集中。这个缺陷也是论文第 6 章「测试发现的问题与改进」的核心素材。

安全决定 1

辖区照旧

规则包在 setup 里把每条规则的根目录登记进路径策略；未登记的路径内核仍然拒绝。规则是「申请」，不是「授权」。

安全决定 2

清空白名单

C:\Windows\System32\LogFiles 这类目录受保护但内容可重建，用 addClearRoot() 只放行「清空内容」，目录本身仍不可删。

安全决定 3

默认收紧

高风险分类（浏览器密码 / Cookie、Windows.old、Downloads 大文件）与 deep_only 规则默认不装载，需在设置里显式打开。

一个可验证的安全信号 规则审计报告显示：本机可命中的 136 个根目录中，有 17 个在登记辖区后仍被路径策略拦截。 这不是规则写错了，而是恰好证明「即使规则想清受保护目录，内核也不会放行」。

v0.3.1 修复

流式输出与可取消

ai/analyze 优先走 SSE：逐块累积文本与思维链，实时发出 ai/stream 事件；取消按钮通过 AbortSignal 立即中断请求。

  • 流式失败或无内容 → 自动回退非流式请求；
  • 请求超时与用户取消分别归类，界面显示可读原因；
  • 非流式计时改为读完 body 再计时，避免把 8 秒显示成 0.2 秒（D-13）。
