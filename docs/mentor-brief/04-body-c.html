把「清理域」而非「清理条目」作为插件粒度：用 Cordis fiber 管理生命周期、配置、启停与故障隔离，插件只依赖契约层。

可能被问到的 8 个问题

Q1和 CCleaner 这类工具的核心区别是什么？+

定位不同：本项目不是功能堆叠，而是验证「清理能力 = 插件」这一架构命题。三个结构性差异：清理域是独立插件（独立生命周期、配置、故障隔离）；删除统一走安全链（白名单辖区 + 防伪票据 + 执行器复核）；规则数据化（271 条规则，加规则不改代码）。AI 只做建议，不直接执行。

Q2插件化是不是过度设计？+

清理软件恰恰需要：规则增长快、删除高危、不同用户想裁剪不同功能。成本主要是插件管理器与生命周期（1 个服务 + 11 个包），实测顺序加载 11 个插件约 18 ms；收益是扩展零内核改动、故障隔离、热重载。规则规模小时也可以只用规则库——项目里两层都有：插件负责「域」，规则库负责「条目」。

Q3AI 会不会误删文件？+

四道约束：① 画像脱敏，不发送路径 / 文件名 / 用户名；② 只建议不执行，必须用户勾选；③ AI 建议不会绕过安全链，和普通清理项走同一条补偿链；④ 生成的插件先静态校验并人工审阅。另有外发审计，能查每次发了什么。

Q4安全性怎么证明，不能只说「我做了检查」？+

三类证据：① 攻击测试覆盖尾点 / 8.3 短名 / UNC / junction 穿透等 9 类绕过；② 结构约束（私有 Symbol 票据、执行器 recheck、白名单辖区），不是靠流程自觉；③ 真实缺陷 D-01：自测发现辖区联接点可导致越界删除，随后修复并补回归测试。所有删除测试都在临时沙箱中执行。

Q5这个题的工作量够吗？+

可量化：源码约 1.93 万行、测试 0.63 万行、脚本 0.57 万行；151 次提交；11 个插件、38 个任务、271 条规则；13 份文档、64 条缺陷记录；385 个自动化测试 + 端到端 + 性能基准。核心贡献集中在「插件化 + 安全链 + 规则库 + AI 边界」，不是 CRUD 堆量。

Q6为什么选 Cordis，而不是自己写插件系统？+

需要的能力恰好是它的强项：服务 DI、fiber 生命周期、effect 自动回收、Schemastery 配置校验、热重载。自己写会把时间花在生命周期与依赖管理上，偏离论文重点（清理架构与安全）。同时插件只依赖契约层，保留了替换框架的可能。

Q7性能怎么样？扫描会不会很慢？+

基准数据：内核启动 5.4 ms、完整启动 162.6 ms；扫描 4,000 个文件 0.15 s（35.9k 文件/秒）；删除 2,178 文件/秒；路径校验 10.4 µs。扫描默认并发 3、进度 120 ms 节流，界面不卡；长任务可取消并返回半成品报告。

Q8有哪些没做完的？下一步做什么？+

仅 Windows；插件没有真正沙箱（加载即全权限，需签名 / 审阅）；永久删除下目录仍可能部分完成；AI 离线不可用；没有代码签名安装包；计划任务型启动项只报告。后续：插件签名与市场、多计划调度、句柄占用主动探测、低配机性能与兼容性评测。

回答原则：先给结论，再给证据（测试 / 缺陷 / 基准），最后主动说局限。不夸大「百分之百安全」。

“CordClean 想证明的不是「我能清理多少垃圾」，而是：
当清理能力可以被装、被卸、被审计，删除这件事才真正可控。”
