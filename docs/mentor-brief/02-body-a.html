01Background & Goal

选题背景：清理工具的问题，不在「清得不干净」

市面上的清理软件并不少，但它们普遍存在三个结构性问题：规则写成代码、删除是黑盒、扩展依赖发版。 本课题把「清理能力」从功能里拆出来，做成依赖 Cordis 插件框架的独立插件，并用一条显式的安全链约束所有删除行为。

问题一

规则硬编码，扩展成本高

每增加一个清理域（新软件缓存、新游戏平台）都要改代码、重新发版；规则散落在各功能模块里，无法审计、无法裁剪。

本课题：数据驱动规则库 + 插件化清理域
问题二

删除是黑盒，误删不可逆

用户只看到「已清理 3.2 GB」，却不知道删了什么、是否可恢复；一旦路径判断错误，删除无法回滚。

本课题：补偿链 + 防伪票据 + 诚实计量
问题三

AI 只会聊天，不能落地

大模型接口变化极快，写死接口就要频繁发版；若让模型直接触发删除，又会被幻觉放大成数据事故。

本课题：可替换适配层 + 只建议不执行
三个研究问题（对应论文第 3、4 章） RQ1：插件化能否让清理能力的扩展做到「加插件/加数据，不改内核」？
RQ2：删除不可回滚，如何用「辖区白名单 + 七步补偿链 + 唯一入口」把它变成可验证的工程约束？
RQ3：在大模型接口快速演进的前提下，AI 如何既用得上、又不越权？

02Architecture

总体架构：四种外壳，一个内核

系统分成 外壳层 / 传输层 / 内核层 / 插件层 / 契约层 五层。浏览器与 Electron 共用同一份内核与界面， 差异只在传输方式与一个很小的 ShellAdapter。插件只依赖契约层，不依赖内核实现 —— 这是「可插拔」成立的前提。

外壳层 · Shell

可替换

同一个内核，可以跑在浏览器里，也可以跑在 Electron 窗口里；界面代码只写一份，外壳差异被压到最小。

apps/webapps/desktoppackages/ui
浏览器外壳：HTTP 静态资源 + WebSocket JSON-RPC；启动时注入随机 token，只监听 127.0.0.1，防止本机其它网页调用高权限接口。
Electron 外壳：contextIsolation + nodeIntegration: false，preload 只暴露最小 invoke 接口。
外壳差异（打开目录、退出应用等）通过 ShellAdapter 注入，UI 层不感知运行环境。
一次清理的数据流
扫描 只产出候选 → 用户勾选 可先 dryRun → compensate.issue 七步检查 → CleanTicket 防伪令牌 → Executor 逐项复核 → 回收站 / 隔离区 → 诚实计量 + 历史
关键设计：依赖倒置 插件看到的是 ctx.cleaner / ctx.pathPolicy / ctx.evaluator 这样的能力契约（由 declare module 'cordis' 做类型增强）， 不依赖内核实现。因此内核可以替换实现而不影响插件，插件也可以被内核在运行时装卸 —— 这是插件化能够成立的结构性前提。
03Plugin System

插件机制：本文最核心的设计

每个清理能力都是一个独立的 Cordis 插件：有自己的 package.json、配置 schema、生命周期与清理辖区。 内核负责装载与回收，插件只负责「申报候选」，永远不直接删除文件。

Cordis 概念在本系统中的用法
class X extends Service内核服务：Settings / System / PathPolicy / Quarantine / History / Cleaner / Compensate / PluginManager
static inject声明依赖顺序；未 inject 就访问会在启动期报错，避免空指针
ctx.plugin(plugin, config)插件管理器装载清理插件；内核装配时装载服务
ctx.effect(() => dispose)注册清理任务、声明清理辖区；插件卸载时框架自动回收，不会泄漏
Config（Schemastery）校验插件配置，同时用于「插件配置界面」的默认值推导
fiber.update(config)改配置后热重载；校验失败不会破坏正在运行的实例
ctx.emit / ctx.on进度与状态事件：cleaner/scan-progress、cleaner/clean-done、plugins/changed

装载：按需懒加载

清单只保存元数据与 load: () => import()，插件模块只在被启用时才载入内存 —— 既是启动性能优化，也是「可裁剪」的体现。

懒加载manifest
相同的调用，不同的阶段
const fiber = ctx.plugin(pluginModule, config)
await fiber                      // setup 完成才视为 active

fiber.update(nextConfig)         // 校验通过后热重载
await fiber.dispose()            // 任务、辖区、监听一起回收
工程细节

任务归属的「差分」技巧

插件管理器需要知道「某个任务属于哪个插件」，但让插件自报 id 会引入耦合。做法是：装载前后各取一次任务 id 集合，差集即归属。

const before = new Set(ctx.cleaner.list().map(t => t.id))
const fiber  = ctx.plugin(mod, config)
await fiber
const after  = new Set(ctx.cleaner.list().map(t => t.id))
record.taskIds = [...after].filter(id => !before.has(id))
代价：插件必须顺序加载（并发会污染差分结果）。实测 12 个插件约 18 ms，可接受。
扩展方式

新增一个清理能力：4 步

  1. 复制 packages/plugins/temp 为新的插件包，改 package.json；
  2. 用 defineCleanerPlugin + ctx.cleaner.define 实现 scan；
  3. 在 core/src/manifest.ts 加一行清单，把包加入依赖；
  4. pnpm install && pnpm dev:web，插件直接出现在「插件」页。
内核无需任何改动。另一种更轻的方式：在规则库 JSON 里加一段规则。

04Cleaning Engine

清理引擎：扫描与清理彻底分离

扫描只产出候选，不删除任何东西；用户勾选后才进入清理流程。清理时还会二次校验， 并且不信任界面回传的路径 —— 即使前端被篡改，也无法清理辖区外的文件。

Scan

扫描流程

  1. 按 taskIds 组装任务列表；
  2. 任务级并发调度（默认 3），每任务构造独立上下文与 AbortSignal；
  3. 插件 scan() 产出候选，或通过 emit() 流式上报；
  4. 规范化 id = sha1(taskId + path) → 路径策略校验 → 按 pathKey 去重；
  5. 进度事件 120 ms 节流，最终汇总 ScanReport。
单任务默认上限 2 万项，超出标记 truncated；错误最多保留 200 条。
Clean

清理流程

  1. 按 itemId 从最近一次扫描结果中重新解析，不信任界面回传；
  2. 按 taskId 分组：有自定义 clean 的走插件，其余走通用删除；
  3. 统一进入 compensate.issue()，通过后签发 CleanTicket；
  4. 执行器逐项复核后执行：回收站 / 隔离区 / 永久删除 / VACUUM；
  5. 汇总诚实计量，非 dryRun 才写历史。
删除并发池上限 6；取消信号贯穿遍历、哈希与删除。
