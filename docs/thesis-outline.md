## 0. 题目与摘要

**中文题目**：基于 Cordis 插件架构的 Windows 安全清理工具的设计与实现
**英文题目**：Design and Implementation of a Windows Safe Cleanup Tool Based on the Cordis Plugin Architecture

**摘要写法（300~500 字，四句话结构）**：

1. 背景与问题：Windows 系统长期使用后产生大量临时文件、缓存与残留注册表项，现有清理软件功能固化、
   模块耦合，用户无法按需裁剪，也难以审计其删除行为的安全性。
2. 本文工作：引入 Cordis 插件架构作为内核，设计并实现了一款 Windows 清理工具 CordClean；
   将每类清理能力抽象为独立插件，通过服务注入（DI）与生命周期管理实现运行时装卸与热配置；
   设计“路径策略—链接祖先—补偿链—执行器—隔离恢复—审计”六层删除安全链，把删除从即时调用
   重构为“申请—复核—签发—执行—回执—恢复”的可复核事务；通过 JSON-RPC 抽象传输层，同一内核
   可运行于浏览器与 Electron 双外壳；AI 只产出建议/草稿，经 schema、路径策略、静态检查与人工确认后
   才可进入系统。
3. 实现结果：系统包含 12 个内置插件（8 个默认启用）、默认 38 个清理任务、73 个 RPC 方法，覆盖系统垃圾、
   浏览器缓存、开发者缓存、磁盘分析、应用残留与启动项等场景；并实现基于 DeepSeek 的 AI 清理顾问与
   插件工坊。
4. 测试结论：95 个测试文件 / 708 个自动化用例全部通过；最近一次 Windows 11 实跑重测（2026-11-23）：
   内核冷启动 6.5 ms、完整启动（38 个任务）167.6 ms、扫描吞吐 25 786 文件/秒、删除吞吐 2 031 文件/秒；
   4 000 个文件扫描 0.16 s、删除 1.97 s。

> “安全”在本文中指删除行为**可约束、可恢复、可审计**，不是杀毒/防护类安全软件。

### 6.3 安全测试

- 尝试清理 `C:\Windows\System32`、`Program Files`、用户文档目录 → 均被拒绝（附返回的拒绝原因）；
- 14 种路径写法（尾点、`..`、混合分隔符、`\\?\`、8.3 短名、大小写、UNC 等）→ 均无法绕过；
- 构造辖区内的 junction 指向外部目录 → 删除被拒绝，外部文件完好（D-01）；
- 递归删除包含 junction 的目录 → 只删链接、不跟随（`tests/fs-safety`）；
- 断网/无权限/文件占用 → 记录失败但不中断，其它项继续；
- 静态资源目录穿越、超大请求体、错误 token → 分别返回 403 / 413 / 401；
- 本地服务：DNS rebinding 形态 Host → 403；错误/缺失 Origin 的 WS → 403；畸形 URL → 400 且服务继续响应（批次1，`tests/host-server.test.ts`）；
- 信任边界：`settings` 原型链污染被拒、`clean/start` 回传 items 被拒、`addClearRoot` 盘符根/保护根及祖先被拒、外部插件越界 target 任务被跳过（批次1，`tests/batch1-hardening.test.ts`、`tests/external-install.test.ts`）。

### 6.4 性能测试

引用 `docs/benchmark.md` 的 Windows 11 实跑快照（2026-11-23），并补充：
- 冷启动 6.5 ms；完整启动（12 插件 / 38 任务）167.6 ms；
- 4 000 个文件扫描 0.16 s（25 786 文件/秒）；删除 4 000 个文件 1.97 s（2 031 文件/秒）；
- 隔离区写入 1.95 ms/项；SHA-256 吞吐 342 MB/秒；常驻内存 RSS 132.6 MB；
- 单次路径校验 10.4 µs（见 `docs/architecture.md` §5.6）；
- 优化前后对比（166 µs → 10.4 µs，扫描吞吐约 4.5k → 25.8k 文件/秒），可作为「性能优化」小节的素材。

### 6.5 结果分析

扫描/删除吞吐与文件数量近似线性；哈希吞吐受磁盘 IO 限制；启动耗时与插件数正相关但绝对值很小；
失败率主要来自文件占用（演示环境 1/3 失败属于正常）。

### 6.7 设计属性验证：E7 插件卸载无残留

已实现 E7 自动化实验（`tests/e7-unload.test.ts`，实验设计与完整数据见
[E7 实验设计](experiments/e7-unload-residue.md)），采用「正例 + 阴性对照」：

| 指标 | 正例加载后 | 正例卸载后 | 反例卸载后 |
| --- | --- | --- | --- |
| 清理任务 | 1 | **0** | **1（残留）** |
| 路径辖区 | 1 | **0** | **1（残留）** |
| UI 贡献 | 1 | **0** | **1（残留）** |
| 定时器（60ms 增量） | 约 5~6 | **0** | **6（仍在跑）** |
| `fiber.getEffects()` | 3 | **0** | 0（但资源仍在） |

结论：`ctx.effect` 登记的资源随 fiber 卸载归零；未登记的资源会残留，且“登记树为空”不能单独证明无残留，必须同时断言应用可观测资源。

**E8 依赖响应（已实现）**：实验代码 `tests/e8-dependency.test.ts`，设计见
[E8 实验设计](experiments/e8-dependency-response.md)。核心结果：

| 操作 | consumer fiber | 任务 | 服务 | setup/teardown |
| --- | --- | --- | --- | --- |
| provider + consumer 启用 | ACTIVE | 有 | 可用 | consumer setup=1 |
| 禁用 provider | **PENDING** | 无 | 不可用 | consumer teardown=1 |
| 重新启用 provider | **自动 ACTIVE** | 有 | 可用 | consumer setup=2 |

整个恢复过程没有手动重启 consumer；插件管理器从 fiber 状态派生 effective status，provider 禁用时 consumer 显示为 `suspended`（「等待依赖」），重新启用后自动恢复 `active`，解决了早期「fiber PENDING 但 UI 仍显示 active」的状态口径问题。

## 创新点表述（答辩用，按开题报告的三条主线）

> 界定：本文不主张算法首创，创新性在“面向清理场景的工程集成”。每条按「对比对象—差异—验证实验」回答，
> 不要把双外壳、规则库、日志系统当成独立创新点；它们放在“系统实现”章节。

1. **面向清理场景的插件契约**：对比 OSGi/Eclipse 的通用模块管理，以及现有清理工具的“XML 规则文件”，
   本文把清理任务、UI 卡片、状态项、命令和页面统一到 Cordis 的 `ctx`/fiber 粒度：`inject` 声明依赖并随
   provider 响应式启停，`ctx.effect` 登记副作用，插件卸载时任务、辖区、UI 贡献和事件一起回退。
   验证：E7（卸载无残留，含“不登记 effect 就残留”的阴性对照）与 E8（provider 禁用后 consumer 自动挂起/
   恢复）；新增清理能力只加插件包，不改扫描器、界面和设置逻辑。
2. **删除过程的事务化**：对比“一次 `fs.rm` + 汇总数字”的现有工具，本文把删除重构为
   “申请—复核—签发—执行—回执—恢复”：路径策略和链接祖先确定可删边界，补偿链在签发前复核存在性、大小、
   修改时间、预览一致性、预算和回收站可用性，执行器只接受 `CleanTicket`（nonce + 5 分钟 TTL 一次性消费，执行前按签发时 size/mtime 复核；递归删除前扫描受保护目录名）并逐项返回结果；取消时按
   `AbortController` 返回已执行部分，隔离区保存可恢复副本与 manifest，回收站返回逐项回执，历史形成撤销与
   审计凭据。验证：危险路径/链接祖先用例、取消后部分结果一致性、隔离区恢复成功率。
3. **AI 产出的准入闭环**：对比“把模型输出直接当规则/代码”的做法，本文把 AI 输出一律按不可信输入处理：
   顾问只接收脱敏画像并输出结构化 JSON；工坊草稿依次过“导出与契约、inject、manifest/权限、语法与危险 API”
   四道静态闸门，再由用户阅读源码确认安装；模型不持有删除接口。验证：AI 形状/隐私/注入/工坊校验用例，
   以及“危险 API 漏检率、一次校验通过率、人工修复率”三个指标。

## 答辩可能提问与回答要点

| 问题 | 回答要点 |
| --- | --- |
| 为什么选 Cordis 而不是自己实现插件机制？ | Cordis 已提供 DI、Fiber 生命周期、effect 回收、配置校验与事件总线；自研需重写这些基础设施，且难以保证正确性。本文的贡献在于"如何在其上建立清理领域模型与安全模型"。 |
| 插件会不会互相干扰？ | 每个插件独立 fiber，卸载时其注册的服务、事件、任务、辖区一并回收；插件启动异常被隔离为 error 状态，不影响其它插件（有测试用例验证）。 |
| 怎么保证不误删？ | 六层删除安全链（路径策略—链接祖先—补偿链—执行器—隔离恢复—审计）+ 白名单辖区 + 二次校验 + 不跟随链接；测试中对系统目录与 14 种绕过写法的清理请求全部被拒绝。 |
| 为什么 AI 不直接执行清理？ | 模型存在幻觉，删除不可逆；因此 AI 只产出建议，且发送的画像不含路径与文件名。 |
| 性能如何？ | 扫描 **25 786 文件/秒**、删除 **2 031 文件/秒**、完整启动 167.6 ms、内核启动 6.5 ms（Windows 11 实跑快照，见 `docs/benchmark.md`）；瓶颈在磁盘 IO 而非 CPU。 |
| 与 CCleaner 的区别？ | 不是功能对标，而是架构验证：可裁剪、可扩展、可审计；安全模型更保守（隔离区、白名单、本地服务 token + Host/Origin 校验）。 |
| 自测中发现过什么问题？ | 共 76 个（D-01~D-76），见 `docs/defect-log.md`。代表性：①辖区内 NTFS 联接点可让删除穿透到辖区外（已加祖先链接检查）；②路径校验早期 166 µs/次拖慢扫描，重构后降到 10.4 µs；③批次1 修复本地服务 DNS rebinding/跨站 WS 调用与 settings 原型污染。 |
| 工作量体现在哪？ | 12 个插件包 + 16 个内核服务 + 73 个 RPC 方法 + 双外壳 + 9 个界面视图（E2E 覆盖 6 个）+ **708 个测试用例** + 插件审计与 E2E 工具 + 性能基准。 |
