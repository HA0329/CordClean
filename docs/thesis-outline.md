## 0. 题目与摘要

**中文题目**：基于 Cordis 插件框架的模块化电脑清理工具设计与实现
**英文题目**：Design and Implementation of a Modular PC Cleanup Tool Based on the Cordis Plugin Framework

**摘要写法（300~500 字，四句话结构）**：

1. 背景与问题：Windows 系统长期使用后产生大量临时文件、缓存与残留注册表项，现有清理软件功能固化、
   模块耦合，用户无法按需裁剪，也难以审计其删除行为的安全性。
2. 本文工作：引入 Cordis 插件框架作为内核，设计并实现了一款模块化清理工具 CordClean；
   将每类清理能力抽象为独立插件，通过服务注入（DI）与生命周期管理实现运行时装卸与热配置；
   设计了"路径策略—隔离区—注册表备份"三层安全模型；通过 JSON-RPC 抽象传输层，同一内核可运行于
   浏览器与 Electron 双外壳。
3. 实现结果：系统包含 11 个内置插件（8 个默认启用）、默认 38 个清理任务，覆盖系统垃圾、浏览器缓存、
   开发者缓存、磁盘分析、应用残留与启动项等场景；并实现基于 DeepSeek 的 AI 清理顾问插件。
4. 测试结论：49 个测试文件 / 366 个自动化用例全部通过；实测内核冷启动 5.4 ms、完整启动（38 个任务）162.6 ms、
   扫描吞吐 26 770 文件/秒、删除吞吐 2 178 文件/秒；4 000 个文件扫描 0.15 s、删除 1.84 s。

**关键词**：插件化架构；Cordis 框架；依赖注入；系统清理；安全删除

### 6.3 安全测试

- 尝试清理 `C:\Windows\System32`、`Program Files`、用户文档目录 → 均被拒绝（附返回的拒绝原因）；
- 14 种路径写法（尾点、`..`、混合分隔符、`\\?\`、8.3 短名、大小写、UNC 等）→ 均无法绕过；
- 构造辖区内的 junction 指向外部目录 → 删除被拒绝，外部文件完好（D-01）；
- 递归删除包含 junction 的目录 → 只删链接、不跟随（`tests/fs-safety`）；
- 断网/无权限/文件占用 → 记录失败但不中断，其它项继续；
- 静态资源目录穿越、超大请求体、错误 token → 分别返回 403 / 413 / 401；
- 本地服务：DNS rebinding 形态 Host → 403；错误/缺失 Origin 的 WS → 403；畸形 URL → 400 且服务继续响应（批次1，`tests/host-server.test.ts`）；
- 信任边界：`settings` 原型链污染被拒、`clean/start` 回传 items 被拒、`addClearRoot` 盘符根/保护根及祖先被拒、外部插件越界 target 任务被跳过（批次1，`tests/batch1-hardening.test.ts`、`tests/external-install.test.ts`）。

### 6.4 性能测试

引用 `docs/benchmark.md` 的表格（2026-10-20 重跑），并补充：
- 冷启动 5.4 ms；完整启动（11 插件 / 38 任务）162.6 ms；
- 4 000 个文件扫描 0.15 s（26 770 文件/秒）；删除 4 000 个文件 1.84 s（2 178 文件/秒）；
- 隔离区写入 1.29 ms/项；SHA-256 吞吐 366 MB/秒；常驻内存 RSS 132.2 MB；
- 单次路径校验 10.4 µs（见 `docs/architecture.md` §5.6）；
- 优化前后对比（166 µs → 10.4 µs，扫描吞吐约 4.5k → 26.8k 文件/秒），可作为「性能优化」小节的素材。

### 6.5 结果分析

扫描/删除吞吐与文件数量近似线性；哈希吞吐受磁盘 IO 限制；启动耗时与插件数正相关但绝对值很小；
失败率主要来自文件占用（演示环境 1/3 失败属于正常）。

## 创新点表述（答辩用，谨慎但不心虚）

1. **插件即清理能力**：以 Cordis 的 DI + Fiber 生命周期为基础设施，把"清理能力"标准化为可装卸的插件单元，
   内核零改动即可扩展，并用「任务归属差分」实现插件与引擎的解耦；
2. **白名单式安全模型**：提出"路径策略 + 隔离区 + 注册表备份"三层防护，其中路径策略采用
   **辖区声明（allowRoot）** 而非黑名单过滤，使插件无法越权，且辖区随插件生命周期自动回收；
3. **传输层与内核解耦的双外壳架构**：以 JSON-RPC 为边界，同一内核与界面可在浏览器与 Electron 中运行；
4. **引入大模型作为"建议者"而非"执行者"，并把接口做成可演进**：AI 插件只输出结构化建议、发送前对画像脱敏；同时用「适配层 + 配置 + `extraBody`」三层设计，使厂商更换模型名、新增推理等级或更换接口形态时无需改代码即可适配。
   删除动作仍由用户确认与路径策略约束。

## 答辩可能提问与回答要点

| 问题 | 回答要点 |
| --- | --- |
| 为什么选 Cordis 而不是自己实现插件机制？ | Cordis 已提供 DI、Fiber 生命周期、effect 回收、配置校验与事件总线；自研需重写这些基础设施，且难以保证正确性。本文的贡献在于"如何在其上建立清理领域模型与安全模型"。 |
| 插件会不会互相干扰？ | 每个插件独立 fiber，卸载时其注册的服务、事件、任务、辖区一并回收；插件启动异常被隔离为 error 状态，不影响其它插件（有测试用例验证）。 |
| 怎么保证不误删？ | 四层防护（路径策略 + 链接祖先检查 + 隔离区 + 注册表备份）+ 白名单辖区 + 二次校验 + 不跟随链接；测试中对系统目录与 14 种绕过写法的清理请求全部被拒绝。 |
| 为什么 AI 不直接执行清理？ | 模型存在幻觉，删除不可逆；因此 AI 只产出建议，且发送的画像不含路径与文件名。 |
| 性能如何？ | 扫描 **26 770 文件/秒**、删除 **2 178 文件/秒**、完整启动 162.6 ms、内核启动 5.4 ms；瓶颈在磁盘 IO 而非 CPU。 |
| 与 CCleaner 的区别？ | 不是功能对标，而是架构验证：可裁剪、可扩展、可审计；安全模型更保守（隔离区、白名单、本地服务 token + Host/Origin 校验）。 |
| 自测中发现过什么问题？ | 共 29 个（D-01~D-29），见 `docs/defect-log.md`。代表性：①辖区内 NTFS 联接点可让删除穿透到辖区外（已加祖先链接检查）；②路径校验早期 166 µs/次拖慢扫描，重构后降到 10.4 µs；③批次1 修复本地服务 DNS rebinding/跨站 WS 调用与 settings 原型污染。 |
| 工作量体现在哪？ | 11 个插件包 + 8 个内核服务 + 55 个 RPC 方法 + 双外壳 + 6 个界面页面 + **366 个测试用例** + 插件审计与 E2E 工具 + 性能基准。 |
