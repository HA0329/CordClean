## 0. 题目与摘要

**中文题目**：基于 Cordis 插件框架的模块化电脑清理工具设计与实现
**英文题目**：Design and Implementation of a Modular PC Cleanup Tool Based on the Cordis Plugin Framework

**摘要写法（300~500 字，四句话结构）**：

1. 背景与问题：Windows 系统长期使用后产生大量临时文件、缓存与残留注册表项，现有清理软件功能固化、
   模块耦合，用户无法按需裁剪，也难以审计其删除行为的安全性。
2. 本文工作：引入 Cordis 插件框架作为内核，设计并实现了一款模块化清理工具 CordClean；
   将每类清理能力抽象为独立插件，通过服务注入（DI）与生命周期管理实现运行时装卸与热配置；
   设计了"路径策略—隔离区—注册表备份"三层安全模型；通过 JSON-RPC 抽象传输层，同一内核可运行于
   浏览器与 Electron 双外壳。
3. 实现结果：系统包含 13 个清理插件、15 个清理任务，覆盖系统垃圾、浏览器缓存、开发者缓存、
   磁盘分析、应用残留与启动项等场景；并实现基于 DeepSeek 的 AI 清理顾问插件。
4. 测试结论：26 个自动化用例全部通过；实测内核冷启动 3.9 ms、全插件加载 17.8 ms、
   扫描吞吐 7284 文件/秒、删除吞吐 3539 文件/秒；全量扫描本机 1721 项、可释放 2.39 GB，耗时 7.3 s。

**关键词**：插件化架构；Cordis 框架；依赖注入；系统清理；安全删除

## 创新点表述（答辩用，谨慎但不心虚）

1. **插件即清理能力**：以 Cordis 的 DI + Fiber 生命周期为基础设施，把"清理能力"标准化为可装卸的插件单元，
   内核零改动即可扩展，并用「任务归属差分」实现插件与引擎的解耦；
2. **白名单式安全模型**：提出"路径策略 + 隔离区 + 注册表备份"三层防护，其中路径策略采用
   **辖区声明（allowRoot）** 而非黑名单过滤，使插件无法越权，且辖区随插件生命周期自动回收；
3. **传输层与内核解耦的双外壳架构**：以 JSON-RPC 为边界，同一内核与界面可在浏览器与 Electron 中运行；
4. **引入大模型作为"建议者"而非"执行者"**：AI 插件只输出结构化建议，且发送前对画像做脱敏，
   删除动作仍由用户确认与路径策略约束。

## 答辩可能提问与回答要点

| 问题 | 回答要点 |
| --- | --- |
| 为什么选 Cordis 而不是自己实现插件机制？ | Cordis 已提供 DI、Fiber 生命周期、effect 回收、配置校验与事件总线；自研需重写这些基础设施，且难以保证正确性。本文的贡献在于"如何在其上建立清理领域模型与安全模型"。 |
| 插件会不会互相干扰？ | 每个插件独立 fiber，卸载时其注册的服务、事件、任务、辖区一并回收；插件启动异常被隔离为 error 状态，不影响其它插件（有测试用例验证）。 |
| 怎么保证不误删？ | 三层防护 + 白名单辖区 + 二次校验 + 不跟随链接；测试中对系统目录的清理请求全部被拒绝。 |
| 为什么 AI 不直接执行清理？ | 模型存在幻觉，删除不可逆；因此 AI 只产出建议，且发送的画像不含路径与文件名。 |
| 性能如何？ | 扫描 7284 文件/秒、删除 3539 文件/秒、全量扫描 7.3 s；瓶颈在磁盘 IO 而非 CPU。 |
| 与 CCleaner 的区别？ | 不是功能对标，而是架构验证：可裁剪、可扩展、可审计；安全模型更保守（隔离区、白名单）。 |
| 工作量体现在哪？ | 13 个插件包 + 8 个内核服务 + 38 个 RPC 方法 + 双外壳 + 6 个界面页面 + 26 个测试用例 + 性能基准工具。 |
